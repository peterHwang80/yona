# Yona vs Company Fit Gap

## 문서 목적

이 문서는 현재 회사 요구사항이 아직 상세히 정리되지 않은 상태에서, "일반적인 사내 협업 서비스 요구"와 원본 Yona 사이의 차이를 초기 가설 형태로 정리한 것이다.  
이 문서는 사실과 가정을 함께 적는다.

## 전제

### 사실

- 현재 확보한 정보는 원본 Yona 소스뿐이다.
- 실제 회사 요구사항 목록, 보안 정책, 운영 정책, 사용자 수, 인증 체계는 아직 제공되지 않았다.

### 가정

- 회사는 사내 협업 서비스로 프로젝트, 이슈, 코드리뷰, 알림을 주로 활용하려 한다.
- UI보다 업무 흐름과 운영 정책의 회사 맞춤화가 우선이다.
- 가능한 한 기존 Yona를 유지한 채 커스터마이징하고 싶다.

## 1. 초기 차이표

| 영역 | 원본 Yona 현재 상태 | 일반적인 사내 요구 | 초기 갭 판단 | 우선도 |
| --- | --- | --- | --- | --- |
| 인증 방식 | 로컬 로그인 + OAuth + LDAP 흔적 | 사내 SSO/OIDC/SAML/AD 연동 | 높음 | High |
| 사용자/조직 동기화 | 수동 생성/관리 중심 | HR/조직도 자동 동기화 | 높음 | High |
| 역할 모델 | 사이트 관리자 / 조직 / 프로젝트 중심의 비교적 단순 RBAC | 세밀한 부서/직무/시스템 권한 | 중간 이상 | High |
| 프로젝트 공개범위 | `PUBLIC / PROTECTED / PRIVATE` | 사내 정책에 맞는 기본값/제한/승인 | 중간 | Medium |
| 이슈 상태 모델 | 기본적으로 `OPEN / CLOSED` 중심 | 승인/대기/검수 등 상세 상태 | 높음 | High |
| PR 정책 | reviewer count, merge, branch delete/restore 내장 | 사내 리뷰/승인 절차, 브랜치 정책 | 높음 | High |
| 알림 채널 | Watch + 이메일 + 웹훅 | 사내 메신저/봇/채널 연동 | 중간 | Medium |
| 브랜딩/용어 | Yona/Yobi 명칭 혼재 | 회사 제품명/용어 체계 | 높음 | Safe |
| 감사/감사로그 | 이벤트/히스토리 일부 존재 | 더 강한 감사 추적, 접근 감사 | 중간 이상 | Medium-High |
| 운영/모니터링 | 구형 Play 로그/설정 중심 | 표준 모니터링, 대시보드, 배포 자동화 | 높음 | High |
| 저장소 지원 범위 | Git + SVN 모두 지원 | 대체로 Git 중심 | 단순화 여지 큼 | Medium |
| 메일 기반 입력 | IMAP 이메일 -> 이슈/댓글 | 보안상 금지 또는 제한 가능성 | 정책 확인 필요 | Medium-High |

## 2. 가장 먼저 확인해야 할 회사 요구사항

아직 확정되지 않았지만, 아래 항목이 정해져야 본격 구현 우선순위가 안정된다.

1. 로그인은 로컬 계정으로 갈지, 사내 SSO로 갈지
2. 조직/부서 정보를 수동 관리할지, 외부 시스템에서 동기화할지
3. 프로젝트/이슈/PR에서 회사가 실제로 쓰는 상태와 승인 절차가 무엇인지
4. 이메일/웹훅/메신저 중 어떤 알림 채널을 허용할지
5. SVN을 유지할지, Git-only로 단순화할지

## 3. 회사 맞춤화 난이도별 후보

### 빠르게 맞출 수 있는 영역

- 제품명/문구/브랜딩
- 메뉴 구성과 기본 landing page
- 프로젝트 메뉴 노출 정책
- 프로젝트 공개범위 기본값

### 구조를 이해한 뒤 맞춰야 하는 영역

- 로그인/계정 정책
- 조직/멤버십 정책
- 이슈 상태/필드/알림 정책
- PR 승인 정책

### 장기 과제로 보는 것이 맞는 영역

- 빌드/배포 체계 현대화
- Play 업그레이드
- Ebean/레거시 프론트엔드 대체
- 저장소 계층 재설계

## 4. 회사용 1차 도입 시나리오 제안

### 판단

회사 요구사항이 아직 상세하지 않다면, 아래 순서가 현실적이다.

1. 브랜딩과 용어를 회사 맞춤으로 정리
2. 프로젝트/조직/권한 정책을 사내 운영 방식에 맞춤
3. 이슈와 PR의 기본 워크플로우를 회사 방식으로 조정
4. 알림 정책을 정리
5. 저장소/메일박스/업그레이드 같은 고위험 축은 마지막에 검토

## 5. 지금 기준의 회사 적합성 평가

| 항목 | 평가 | 근거 |
| --- | --- | --- |
| 협업 플랫폼의 기본 기능성 | 높음 | 프로젝트, 이슈, PR, 코드리뷰, 알림이 이미 갖춰져 있음 |
| 회사 맞춤 UI/용어 변경 용이성 | 높음 | 서버 렌더링 템플릿과 메시지 파일 구조가 명확함 |
| 권한/정책 맞춤화 가능성 | 중간 | 가능하지만 `AccessControl`과 모델 로직 이해가 선행돼야 함 |
| 사내 표준 인프라 적합성 | 중간 이하 | 빌드/도구/외부 의존성이 오래됨 |
| 장기 유지보수 적합성 | 중간 이하 | 레거시 스택과 두꺼운 모델/컨트롤러 구조 때문 |

## 6. 최종 해석

### 사실

- Yona는 기능 측면에서는 사내 협업 서비스의 출발점으로 충분히 풍부하다.
- 하지만 운영 표준화, 인증 통합, 빌드 재현성 측면에서는 추가 작업이 필요하다.

### 판단

- "기능이 부족해서 못 쓰는 제품"은 아니다.
- 오히려 "기능은 충분하지만, 회사 표준 운영과 정책에 맞추기 위한 이해/정리 비용이 큰 제품"에 가깝다.
- 따라서 첫 단계는 기능 추가보다 요구사항 정리와 커스터마이징 안전지대 확보가 맞다.
